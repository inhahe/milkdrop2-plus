# MilkDrop 2 Plus: design

How the component is put together, for whoever changes it next. [README](README.md) is the user's view; this is the maintainer's.

## Parts

| Part | What it is |
|---|---|
| `foo_vis_milk2/` | The foobar2000 component (`foo_milkdrop2_plus.dll`): the Default UI element (`ui_element.cpp`, which also `#include`s `keyboard.cpp` and the Columns UI element `cui_element.cpp`, compiled in whenever the `external/columns_ui-sdk` submodule is checked out, as in the release build (`pch.h` then sets `HAS_COLUMNS_UI`); that element has no context menu), preferences and advanced settings (`preferences.cpp`, `config.h`), the preset browser and categories (`preset_browser.*`), favorites (`favorites_manager.*`), and how saved paths are stored (`stored_path.*`). |
| `vis_milk2/` | The MilkDrop 2 engine, a static library: `CPlugin` (`plugin.cpp`: presets, menus, text overlay), its shell (`pluginshell.cpp`: window, timing, drawing order), rendering (`milkdropfs.cpp`), preset state and equations (`state.cpp`), a Direct3D 9-style shim over Direct3D 11 (`d3d11shim.cpp`), Direct2D/DirectWrite text (`textmgr.cpp`), the texture cache's limits and which texture it drops first (`texture_cache.*`), and the component's own text files (`utf8_file.*`). |
| `external/` | Dependencies. `eel2/`, `nu/`, `winamp/data/` (the shader files shipped in the component's `data` folder), `dxtk/` (the DirectXTK sources used) are in the repository; `columns_ui-sdk/` is a submodule, which a recursive clone fetches; the foobar2000 SDK, PFC, libPPUI, projectM-EEL and WTL are fetched and patched as BUILDING.md describes. |
| `test/` | CppUnitTest tests, run with `vstest.console.exe` on `Bin\<platform>\<config>\test.dll`. |
| `install-milkdrop2-plus.cmd` | The one-file installer for users, which installs a release: see [One-file installer](#one-file-installer). |

## Rendering

Each frame (`CPlugin::RenderFrame`, `milkdropfs.cpp`) works on two textures that swap roles every frame, VS0 (last frame) and VS1 (this frame):

1. Motion vectors are drawn into VS0.
2. The warp pass draws VS0, warped and faded by the preset, into VS1. With no preset loaded (the state's description is `INVALID_PRESET_DESC`), VS1 is cleared to black instead: there is no warp to fade old content, and without the clear each texture keeps everything ever drawn into it and the picture flickers between the two.
3. Blur passes, then custom shapes, custom waves, the main wave and sprites are drawn into VS1. A song title animation that has just ended is stamped into VS1 here.
4. The composite pass draws VS1 to the back buffer; the running song title animation and user sprites go on top.
5. VS0 and VS1 swap.

When a shader is loaded, `CShaderParams::CacheParams` binds its textures and parameters. A texture is looked up by name in every texture folder with every image extension, trying each existing file in turn until one loads (`ForEachTextureCandidate`), so a file WIC cannot decode (a TGA) does not hide a good one further on; a path too long for `MAX_PATH` is normalized and gets the `\\?\` prefix (`LongPathSafe`). Folder listings (random picks, a pack's top folder, the count shown) leave TGAs out (`IsTextureFileName`). A random texture (`randNN`) is picked from a list of the texture folders' images, reread when a folder's last-write time changes or `m_nTextureDirGeneration` moves (the user picked a folder or edited a shader; a FAT folder's time never changes), so images copied in while foobar2000 runs are offered.

The texture folders (`m_textureDir`, and `m_texturePresetDir`, which `SetPresetDir` and each scan set) are guarded by their own lock, `m_textureDirLock`, held only to copy them (`GetTextureDirs`), not by `g_cs`: the render thread holds `g_cs` for a whole frame while it sends the UI thread messages, and a preset loaded from the menu with no blend time still compiles on the UI thread (see known-issues.md), which must not wait on it. The shader editor and the pixel shader upgrade compile on the render thread: they set bits in `m_shaderRequests`, carried out at the start of the next frame (`DoShaderRequests`).

Textures loaded from disk are cached in `m_textures` by name. Before another loads, the cache makes room within the MaxImages and MaxBytes settings (`TextureCacheIsFull`); Auto (-1) sets no limit on the number and, on bytes, a quarter of the adapter's own video memory or a sixteenth of the system memory it may share, whichever is larger, between 64 MB and 1 GB (`AutoMaxTextureBytes`, measured when the device is created). It never drops a texture bound to a shader drawn (the preset on screen, and during a blend the one it comes from) or being compiled, nor one the preset on screen or the one loading used, and otherwise drops the largest, its size weighted up to double the longer ago it was used (`PickTextureToEvict`). Both are in `texture_cache.cpp`, which the tests cover.

A texture found nowhere is left unbound (it samples black) and noted in that shader's own list (`CShaderParams::m_missingTextures`, fixed arrays because the engine copies these objects with `memcpy` and clears them with `ZeroMemory`). At the end of every frame the render thread runs `ReportMissingTextures`, which compares the names both shaders on screen miss with what it last showed and, when they differ (whatever recompiled the shaders: a mash-up, a shader edit, a device reset) or a finished load or a change of folder asked for it (`m_bMissingTexturesReportDue`), shows them in the upper-right corner as `ERR_TEXTURES` messages in place of the previous one, or removes that once nothing is missing. What it last showed is the render thread's alone. `SetTextureDir` (the menu, or the advanced setting through `PanelSettings`) only marks a change of folder; the render thread then, at the first frame no preset is loading in, drops the cached disk textures and binds the shaders on screen afresh (`ReloadDiskTextures`), so the change shows at once.

The shim keeps one current pixel shader; a draw that needs a particular one (for instance `ShowSongTitleAnim`, which needs the textured shader 0) must select it, because the previous draw may have left an untextured one. Before binding a preset shader's textures, `ApplyShaderParams` empties all 16 texture slots (`ClearTextures`) and then binds each sampler's texture at its own texture register, so a sampler whose texture is missing reads black.

A preset's pixel shaders compile at the model its `PSVERSION` lines name (`RecompilePShader`): 2.0 as `ps_4_0_level_9_1`, 2.x and 3.0 as `ps_4_0_level_9_3`, 4.0 as `ps_4_0`, 5.0 as `ps_5_0`. The highest model allowed, `m_nMaxPSVersion`, is the preferences' choice or else the device's (5.0 at feature level 11, 4.0 at 10); the scan leaves presets above it out of its list, though the preset browser can still load them by path. The menu's "upgrade preset's pixel shader model" steps 2.0, 2.x, 4.0, 5.0 (the keys in `keyboard.cpp`, the prompts in `MilkDropRenderUI`) and recompiles both shaders.

Text (preset name, notices, menus) is retained-mode: each line is a `TextElement` registered with `CTextManager`, laid out by `MilkDropRenderUI` each frame, and hidden and unregistered when no longer shown. An upper-right box is one line high, so multi-line notices use one element per line. The upper-right messages (`AddError`, `ClearErrors`) may be added or cleared from any thread: each call queues a request under `m_errorRequestsLock`, and the render thread, the only one that touches `m_errors` and their text elements, carries the queue out at the start of `MilkDropRenderUI` (`ApplyErrorRequests`).

## Presets

- The preset folder is scanned recursively on a background thread (`__UpdatePresetList`), which keeps a cache, `preset_cache.dat`, in the preset folder. The first preset is loaded by `MilkDropRenderFrame` once the scan has finished.
- With the list, the scan thread records under `g_cs` the folder it read (`m_scannedPresetDir`), how many `.milk` files it found there (`m_nPresetFilesFound`) and how many of them the shuffle mode's category and favorites filters keep (`m_nPresetFilesInShuffle`); the list then drops presets that need a newer pixel shader model than allowed. The names in `m_presets` are relative to `m_scannedPresetDir`, so preset paths are built from it (`CPlugin::GetPresetPath`, which takes `g_cs`), not from `m_szPresetDir`, which already names the next folder while its scan runs.
- The folder to scan is changed only through `CPlugin::SetPresetDir`, which refuses a path longer than `MAX_PRESET_DIR_LENGTH` (a scan formats it with `*.*` into a `MAX_PATH` buffer) and takes `g_cs` while that lock exists (from engine initialization to cleanup; before or after, no other thread uses the folder). Cleanup stops the scan thread, which checks for the request at every file, before deleting the lock.
- With no presets, the engine keeps the default state (`CState::Default`): a plain waveform on black. `MilkDropRenderUI` meanwhile shows a notice in the upper-right corner, and the right-click menu says the same at its top: with no files, "No presets found", the command to choose a folder (Set Preset Library Folder) and the folder it looked in; with files that the shuffle mode excludes, that and how to change it; with files kept but none loadable, that. Its advice is the Default UI element's context menu.
- Favorites are stored as paths relative to the preset folder, so they survive moving the folder.

## Settings and files

| What | Where |
|---|---|
| Most settings | foobar2000's configuration (`milk2.*` advanced settings and the preferences page), in `config.sqlite`. |
| Preset folder | `PresetLibraryPath` in `<profile>\browser_config.ini` (read for both elements by `ReadKeyValueFile`), written by Set Preset Library Folder; it overrides the `milk2.szPresetDir` advanced setting when the UI element is created. `milk2_config::build` writes the folder in use back to `milk2.szPresetDir` whenever foobar2000 saves the element's configuration. |
| Shuffle mode, categories | `<profile>\browser_config.ini` |
| Favorites | `<profile>\favorites.ini` |
| Preset scan cache | `preset_cache.dat` in the preset folder |
| Textures | The folder chosen with Set Texture Folder (`milk2.szTextureDir`, saved like the preset folder; empty for none; a folder with no images whose `textures` subfolder has some, such as a texture pack's top folder, stands for that subfolder: `CPlugin::ResolveTextureDir`), then `<profile>\milkdrop2\textures\`, then the top of the preset folder (`CPlugin::GetTextureDirs`). Random textures (`randNN`) are picked from the first two. |
| Sprites, messages | `milk2_img.ini`, `milk2_msg.ini` in `<profile>\milkdrop2\`. |

browser_config.ini, favorites.ini and preset_cache.dat are UTF-8, through `WriteUtf8TextFile`/`ReadTextFile`/`ReadKeyValueFile` (`utf8_file.h`). Writing goes through a temporary file, so a failure leaves the old file whole; reading falls back to Latin-1 line by line, so files from earlier versions still read and one bad line spoils only itself.

Both stores of the preset folder, and the textures folder setting, go through `milk2_config::folder_to_stored`/`folder_from_stored`, and so `ToStoredPath`/`FromStoredPath` (`stored_path.h`): a folder inside the profile, or anywhere inside a portable installation (the profile's parent), is saved relative to the profile, so a moved or copied installation keeps finding it; anything else stays absolute, and absolute values saved by older versions still load. A loaded path gets its trailing backslash there, and one longer than `MAX_PRESET_DIR_LENGTH` is not used; the Default UI element saves such a `PresetLibraryPath` back as it was, so that moving the installation back restores it. When the folder is missing, `FindValidPresetDir` falls back to `<profile>\milkdrop2\presets\`, then `<profile>\milkdrop2\`, then the profile.

## One-file installer

`install-milkdrop2-plus.cmd` installs the latest release, the original MilkDrop presets and the texture pack, and offers a layout, for someone who has only that file and builds nothing. It is a batch file whose first lines PowerShell reads as a block comment (`<# : ... #>`): cmd runs them, copies the file to a temporary `.ps1` (the only kind of file PowerShell runs) and runs that in Windows PowerShell with `-ExecutionPolicy Bypass`. The repository keeps it byte for byte (`-text` in `.gitattributes`), so that GitHub's raw download has CRLF line endings, and its batch part has no labels or blocks, which cmd misreads in a file with LF endings.

It relies on these contracts of the component, so a change to any of them must change it too:

- The profile: `<foobar2000>\profile` when `portable_mode_enabled` exists beside foobar2000.exe, `%APPDATA%\foobar2000-v2` otherwise; components in `user-components-x64\<DLL name>\`.
- Every name the component's DLL has had (`$ComponentNames`: `foo_vis_milk2` until v0.2.1, `milkdrop2_plus` from an earlier `install.bat`, `foo_milkdrop2_plus` since; `uninstall.bat` lists the same three). All register the Default UI element `guid_milk2`, so it moves the others aside; it also looks for that GUID in a layout.
- A running foobar2000 keeps its profile's `config.sqlite` open, which is how it tells that foobar2000 is running with the profile it is about to change.
- `PresetLibraryPath` in `browser_config.ini`, which it sets to `milkdrop2\presets\`, relative to the profile (`FromStoredPath`, v0.3.0 and later), keeping the file's other lines and their encodings as [Settings and files](#settings-and-files) describes.
- Textures in `<profile>\milkdrop2\textures\`.
- The release asset: one `*.fb2k-component`, a zip with one DLL at its top.

Each run that changes the profile keeps a backup folder, `<profile>\milkdrop2-plus-install-backup\<date and time>\`. It holds what the run moved away (component folders, `theme.fth`) at the same place relative to the profile, and a manifest, `run.txt`, with a line written before each change: its sequence number and kind (install, restore, or undone), then `saved <path>`, `absent <path>` (the run put something where there was nothing), and `setting`/`nosetting` with the new and old raw values of a key it changed in an ini file (only `PresetLibraryPath`, so a restore leaves the plugin's other settings alone). Runs are ordered by sequence number, not date; a manifest the script cannot read is passed over with a warning. `-Restore` undoes the newest install from its manifest, newest change first, and touches nothing the manifest does not list: it skips an item missing from the backup, with a warning, and a setting changed since the install. If a step fails it reverses the steps so far, so the backup stays whole, and says what it could not reverse. What it displaces goes into a backup of kind restore, which `-Restore` passes over, so the next `-Restore` undoes the install before. A backup an earlier version made has no manifest and counts as older than any other: its components and `theme.fth` go back, its copy of `browser_config.ini` gives the old `PresetLibraryPath`, and, as such a run also installed a component, the other components are taken out. Presets and textures are not tracked; a run only ever adds them.

The layout it offers is a Default UI `theme.fth`, embedded in base64 at the end of the file and taken from a working installation. The MilkDrop element's configuration in a layout is only the `MILK` sentinel and the version (`milk2_config::build`), with no paths, so the layout works in any profile. To offer another, embed its `theme.fth` and change `$EmbeddedLayoutDescription`.

## Build

- `milkdrop2-plus.sln`, Visual Studio 2026 (toolset v145). The release package is the x64 Release DLL plus `data\` (`external\winamp\data\*.fx` and `vis_milk2\help.bin`), zipped as `milkdrop2-plus.fb2k-component`. Each release also carries `install-milkdrop2-plus.cmd` as an asset (`gh release upload <tag> install-milkdrop2-plus.cmd`): the README's One-File Install links to `releases/latest/download/install-milkdrop2-plus.cmd`, which a release without it breaks. After a change to the installer, upload it to the latest release again, with `--clobber`, or that link keeps serving the old one.
- `Directory.Build.props` (through `ForceImportBeforeCppProps` and `toolset.props`) sets toolset v145, and `Directory.Build.targets` the statically linked C/C++ runtime, for every project in the tree, including the foobar2000 SDK projects whose project files are not ours; our own project files set neither, so these are the only place to change them. foobar2000 loads one copy of the DLL runtime for the whole process, from its own folder, and it can be older than our compiler (foobar2000 2.26 ships 14.44; v145 code needs 14.50 or later); a runtime linked into the DLL does not depend on it. Every library linked in must use the same runtime, which is why DirectXTK is built from source (`external/dxtk`) rather than taken from NuGet, whose libraries use the DLL runtime.
- v145 code needs Windows 10 or later.
